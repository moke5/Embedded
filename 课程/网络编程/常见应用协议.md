## HTTP分析与应用

### **1. HTTP协议概览**

HTTP协议是 `Hyper Text Transfer Protocol`（超文本传输协议）的缩写，平时上网时，浏览器基本都是基于该协议与服务器通信的，HTTP是基于 `TCP/IP` 协议来传输数据的，包括HTTP文件、图片、查询结果等。

HTTP是一个典型的 C/S （即`client-server`）协议：请求通过一个实体被发出，实体也就是用户代理。大多数情况下，这个用户代理都是指浏览器，当然它也可能是任何东西，比如一个爬取网页生成维护搜索引擎索引的机器爬虫。

每一个发送到服务器的请求request，都会被服务器处理并返回一个消息，也就是response。在这个请求与响应之间，还有许许多多的被称为 proxies 的实体，他们的作用与表现各不相同，比如有些是网关，还有些是caches等，如下图所示。

### **2. HTTP的特点**

**（1）简单快速**
客户端向服务器请求服务时，只需传送请求方法和路径。请求方法常用的有 `GET`、`PUT`、`POST`、`HEAD` 等，每种方法规定了客户端与服务器通信的类型。由于HTTP协议非常简单，因此 HTTP 服务器的程序规模小，通信效率高。

**（2）灵活**
HTTP 允许传输任意类型的数据对象。

**（3）无连接**
HTTP 每次连接只处理一个请求，服务器处理完客户的请求并收到客户应答之后，即断开连接。这么做是为了节约服务器套接字文件资源。

一个连接是由传输层来控制的，这不属于HTTP的范围。HTTP并不需要其底层的传输层协议是面向连接的，只需要它是可靠的，或不丢失消息的（至少返回错误），因此一般而言，HTTP 底层使用面向连接的TCP进行消息传递，但要注意连接并不是必须的，基于TCP也不是必须的。

**（4）无状态**
HTTP 协议是无状态的，即 HTTP 自身不对请求和相应之间的通信状态进行保存，任何两次请求之间不存在依赖关系，换句话说就是每个请求都是独立的。

![img](./img/wKgP3GJVOnqAJorNAAHZP2jseRU526.png)
<center>
    HTTP请求与响应
</center>



无状态的设计当然是为了使得 HTTP 协议简单、轻量，但有些时候会略显不便，无状态意味着用户没有办法在同一个网站中进行连续的交互，比如在一个电商网站里，用户把某个商品加入到购物车，切换一个页面后再次添加了商品，这两次添加商品的请求之间没有关联，浏览器无法知道用户最终选择了哪些商品，但 HTTP 是可扩展的，使用HTTP的头部扩展，HTTP Cookies就可以解决这个问题。把Cookies添加到头部中，创建一个会话让每次请求都能共享相同的上下文信息，达成相同的状态。

总体而言，HTTP是好用的，既满足扩展性，又满足易用性。

### **3. HTTP报文**

HTTP通信实际上就是按照HTTP协议的规范，将TCP数据段进一步封装为HTTP数据包发送给对方，以及将对方发来的HTTP数据包按规范逐次拆解的过程。

**典型HTTP请求报文头部**

```
char *http_request = "GET /repo/boa-0.100.9.tgz HTTP/1.1\r\n"
                     "Range:bytes=0-\r\n"
                     "Host:www.boa.org\r\n\r\n";
```

在 HTTP 请求报文中，其格式规范如下：

                    "..."
                    "字段n:值\r\n"

```

#### **4.1 请求报文中的请求行**

**（1）请求方法**
HTTP协议中的请求方法常见的有 `GET`、`HEAD`、`POST`、`PUT` 等等：

- `GET` 一般用来指示从服务器获取资源，服务器返回响应头部和响应包体。
- `HEAD` 一般用来指示检测文件是否存在或判定文件版本，服务器只返回响应头部。
- `POST` 一般用来指示向服务器递交新的 HTML form 表单，实际数据类型一般通过 `attribute` 来决定。
- `PUT` 一般用来指示向服务器递交修改信息。

要注意，**HTTP 并非一种强制协议**，HTTP 有很高的拓展性，因此在实际应用中，客户端发起请求时所使用的的请求方法是由当时具体提供服务的服务端决定的，并不一定遵循上述约定。

**（2）URL**
URL（Uniform Resource Locator，统一资源定位符）指的是所请求的资源在服务主机中的路径。比如：

- 某下载地址：

    ```
    https://cdn.kernel.org/pub/linux/kernel/v5.x/linux-5.17.2.tar.xz
    ```

    - `"https://"` 是协议信息。
    - `"cdn.kernel.org"` 是域名，即主机名
    - `"/pub/linux/kernel/v5.x/linux-5.17.2.tar.xz"` 则是此例中的 URL。

**（3）协议版本**
协议版本，一般写 `HTTP/1.1`即可，具体而言：

- HTTP与1990年问世，版本是 `HTTP/0.9`，当时并未作为正式的标准被建立。
- HTTP作为标准被公布是1996年5月，版本是 `HTTP/1.0`。
- 1997年1月公布 `HTTP/1.1`，记载于 RFC2616，这是目前最被广泛使用、覆盖率最高的 HTTP 协议版本。
- 2013年8月对 `HTTP/2.0` 做了首次合作共事性测试，改版本只适用于 `https://` 网址。

#### **4.2 请求报文中的字段**

HTTP协议的首部字段有很多，并且根据HTTP的设计原则，各种字段是不具备强制性的，只要服务器和客户端约定好相关含义和位置即可通信。

以下是常见的标准字段：

- ```
    Accept
    ```

    ：请求希望服务器能响应何种表现格式。

    - 例如 `"Accept:text/plain\r\n"`，这代表客户端跟服务器说它只接受纯文本数据（不接收图片、视频）。

- `Accept-Encoding`：告诉服务器可以接收何种压缩格式传输，以减少带宽。

- ```
    Range
    ```

    ：请求获得一个资源的部分表示，常与

    ```
    If-Unmodified-Since
    ```

    一起用。

    - 例如 `"Range:bytes=-\r\n"`，代表客户端要求服务器发送资源全文。
    - 例如 `"Range:bytes=-1000\r\n"`，代表客户端要求服务器发送资源的前1000个字节。
    - 例如 `"Range:bytes=100-\r\n"`，代表客户端要求服务器发送资源的第100开始的后面所有字节。

- `If-Modified-Since`：通过前一次响应`Last-Modified`的时间值，当条件不成立，请求成功返回。

- `Host`：用于指明服务器的主机名称。

- `Authorization`：按特定认证方案编码的用户名和密码证书，服务器接收验证通过执行请求。

以下是常见的非标准字段：

- `Cookie`：客户端告诉服务器Cookie属性。HTTP是无状态协议，客户端的多次请求能保持连贯，是因为有Cookie属性的帮助。

#### **4.3 请求报文中的包体**

大多数请求报文中，请求包体可以为空。但要注意，请求报文的首部字段最后要以 `"\r\n"` 结束。

### **5. HTTP响应**

在 HTTP 响应报文中，其格式规范如下：

```
char *responseHead = "协议版本 状态码 状态码描述\r\n"
                    "字段1:值\r\n"
                    "字段2:值\r\n"
                    "字段3:值\r\n"
                    "..."
                    "字段n:值\r\n"
                    "\r\n"
                    "响应包体";
```

#### **5.1 响应报文中的状态行**

**（1）协议版本**
服务器返回其当前所使用的 HTTP 协议版本。

**（2）状态码**
状态码是响应报文中最重要的信息，由3个数字构成，大致可分为以下五大类：

- 1xx：通知。仅在与HTTP服务器沟通时使用。
- 2xx：成功。表示成功收到、理解和接受服务器动作。例如：
    - 200(“OK")
    - 201(“Created")
    - 204(“No Content")
- 3xx：重定向。表示为完成请求，必须进一步采取措施。例如：
    - 301(“Moved Permanently”)
    - 303(“See Other”)
    - 304(“Not Modified”)、
    - 307(“Temporary Redirect”)
- 4xx：客户端错误。代表客户端发出的请求报文有误不能完成。例如：
    - 400(“Bad Request”)
    - 401(“Unauthorized”)
    - 403(“Forbidden”)
    - 404(“Not Found”)，这就是著名的 `404` 错误
    - 405(“Method Not Allowed”)
    - 406(“Not Acceptable”)、
    - 409(“Conflict”)、 410(“Gone”)
- 5xx：服务器端错误。代表服务器无法完成明显合理的请求。例如：
    - 500(“Internal Server Error”)
    - 503(“Service Unavailable”)

更详细的 HTTP 状态码，点击查询 [HTTP状态码详解](https://tool.oschina.net/commons?type=5) 。

#### **5.2 响应报文中的头部字段**

以下是常见的HTTP响应报文头部字段及其含义：

- **`Content-Length`: 给出响应包体的大小，客户端可据此做读取准备，也可通过Head请求来获知。**
- **`Transfer-Encoding`: 给出响应包体的编码形式，若出现该字段且其值为 `chunked`，则代表服务端将以分段方式返回资源数据。**
- `Accept-Ranges`: 表明支持部分Get请求，客户端通过Head请求获取该值，然后发送Range报头请求，获取资源部分表示。
- `Content-Encoding`: 对应`Accept-Encoding`请求报头。
- `Content-Language`: 给出响应包体采用的自然语言，对应`Accept-Language`请求报头，可能多个值。
- `Content-Location`: 把请求资源的规范URI告知客户端，但并不要求其使用新URI。
- `Content-MD5`: 实体主体MD5,可检测错误损坏。
- `Last-Modified`: 资源表示的最后修改时间。
- `ETag`: 比Last-Modified更精确，能反映1秒内变化。
- `Expires`: 客户端可在一段时间内缓存整个响应（不光是实体主体），但服务器不保证该时间段内一定不更新。
- `Location`: 与3xx系列响应密切相关，可表示新资源创建后的URI，也可表示默认URI，还可是补充建议URI。
- `WWW-Authorization`: 配合401 Unauthorized响应代码，可指定认证方式WSSE等。

对上述前两个响应报文字段要作特别的说明：

- **`Content-Length`**
- **`Transfer-Encoding`**

一般而言，当客户端向服务器请求资源（比如请求下载某文件、查询某信息等），服务器都需要告诉客户端其所申请的数据总量，以便于客户端可以准备恰当的内存来存储对应数据。

在通常情况下，服务器会返回 `Content-Length` 直接告诉客户端响应包体总大小，此时响应包体会一次性发送给客户端。

此时的响应报文形如：

```
HTTP/1.1 200 OK
Date: Tue, 12 Apr 2022 07:26:41 GMT
Content-Length: 2889
Connection: keep-alive
...
...

{实际响应包体}
```



但此种简单情况无法应对一些动态数据，比如服务器在发送响应包体结束之前无法得知具体大小，那么就无法采用此种模式，改而采用分块（chunked）发送，每一块数据发送前，都先以十六进制发送此数据块的大小，每个数据块大小和数据块本身都以"\r\n"结束。

此时的响应报文形如：

```
HTTP/1.1 200 OK
Date: Tue, 12 Apr 2022 07:26:41 GMT
Transfer-Encoding: chunked
Connection: keep-alive
...
...

aa3
{响应数据块1}

82
{响应数据块2}

8da
{响应数据块3}
```



可见，在该种情形下，客户端需要读取每块响应包体的长度（注意进制），并根据长度逐块读取响应包体，再拼成最终请求的资源。

#### **5.3 响应报文中的包体**

响应包体中通常包含了客户端所请求的资源，比如请求加载的HTML网页文档、请求下载的文件资源等。



## 云API部署使用

### **1. API云市场简介**

许多公共服务，比如天气、物流、证件申办、AI应用等，在国内各大平台都有开放的API可以直接调用。

比如，某款产品需要实时获得天气信息，开发人员无需研究如何获取相关气象站的信息，也无需研究气象站数据与产品代码的兼容性，直接可从API市场获取指定地址的气象信息，且其数据都是以网络通用的格式封装的（`JSON/XML`等）。

再如，某智能车库需要增加车牌的自动识别，也无需开发人员研究图像识别技术，可直接在API市场调用相关接口，将图片直接识别为车牌字符串返回，这些服务一般都是基于HTTP请求，按用量收费的。

下面是以[心知天气](https://www.seniverse.com/)为例的天气查询核心代码（[forecast.zip](http://vm.yueqian.com.cn:8886/group1/M00/00/40/rBJlJmMMewmAApG-AAF8w2LNs0I204.zip?token=null&ts=null&filename=forecast.zip)）

```
////////////////////////////////////////////////////////
//
//  Copyright(C), 2005-2022, GEC Tech. Co., Ltd.
//  www.yueqian.com.cn  ALL RIGHT RESERVED
//
//  文件: forecast.c
//  描述: 基于HTTP协议的天气查询案例
//        本案例使用心知天气提供商的API接口
//        所有数据处理以该提供商的规范为准，若更改API提供商
//        则相应HTTP请求格式、参数、数据解析都应重新设计。
//
///////////////////////////////////////////////////////

int main(int argc, char **argv)
{
	// 利用DNS服务查询指定域名的IP
	struct hostent *he = gethostbyname("api.seniverse.com");
	if(he == NULL)
	{
		perror("DNS查询失败");
		exit(0);
	}

	printf("IP: %s\n", inet_ntoa(*(struct in_addr*)((he->h_addr_list)[0])));

	struct sockaddr_in addr;
	socklen_t len = sizeof(addr);
	bzero(&addr, len);

	addr.sin_family = AF_INET;
	addr.sin_addr   = *(struct in_addr*)((he->h_addr_list)[0]);
	addr.sin_port   = htons(80);

	// 创建TCP套接字(因为HTTP是基于TCP的)，并发起连接
	int fd = Socket(AF_INET, SOCK_STREAM, 0);
	if(connect(fd, (struct sockaddr *)&addr, len) == 0)
	{
		printf("连接服务器成功！\n");
	}

	// 准备好HTTP的请求报文
	char *s = httprequest();
	write(fd, s, strlen(s));


	// 接收对方的响应头部
	char res[1024];
	int total = 0;
	while(1)
	{
		int n = read(fd, res+total, 1);

		if(n <= 0)
		{
			perror("读取HTTP头部失败");
			exit(0);
		}

		total += n;

		if(strstr(res, "\r\n\r\n"))
			break;
	}

	// 分析响应码，并获取正文的长度
	int ok, jsonlen=0;
	parse(res, &ok, &jsonlen);
	if(!ok || jsonlen == 0)
	{
		exit(0);
	}

	// 接收正文
	char *json = calloc(1, jsonlen);
	total = 0;
	while(jsonlen > 0)
	{
		int n    = read(fd, json+total, jsonlen);
		total   += n;
		jsonlen -= n;
	}

	cJSON *root = cJSON_Parse(json);
	cJSON *body = cJSON_GetObjectItem(root, "results");

	cJSON *a = cJSON_GetArrayItem(body, 0);

	cJSON *now  = cJSON_GetObjectItem(a, "now");

	printf("天气情况: %s\n", cJSON_GetObjectItem(now, "text")->valuestring);
	printf("当前气温 : %s°C\n", cJSON_GetObjectItem(now, "temperature")->valuestring);

	return 0;
}

	{

	char *p;
	if(p = strstr(res, "Content-Length: "))

	else if(p = strstr(res, "Transfer-Encoding: chunked"))
		*len = -1;

## MQTT分析与应用

### **1. MQTT简介**

MQTT（**Message Queuing Telemetry Transport，消息队列遥测传输协议**），是一种基于**发布/订阅（publish/subscribe）模式的"轻量级"通讯协议**，该协议构建于TCP/IP协议上。MQTT最大优点在于，可以以极少的代码和有限的带宽，为连接远程设备提供实时可靠的消息服务。作为一种低开销、低带宽占用的通讯协议，使其在物联网、小型设备、移动应用等方面有较广泛的应用。

![img](./img/rBJlJmO6lUuAa_VhAAECPr9Jto4121.png)

#### **1.1 MQTT的起源和定位**

- 诞生背景
    - 1999年由IBM开发，最初用于石油管道传感器与卫星间的数据传输
    - 2014年成为国际标准（OASIS），专为物联网场景优化：低带宽、高延迟、设备资源受限
- 协议定位
    - 位于TCP/IP协议栈的应用层（对比：HTTP同属应用层，但设计理念不同）
    - 基于TCP实现可靠传输，默认端口1883（非加密）和8883（SSL加密）

#### **1.2 MQTT的核心特点**

- 轻量级设计
    - 固定头部仅2字节，最小报文仅2字节（对比：HTTP头部动辄几百字节）
    - 适合嵌入式设备：例如智能灯泡的MCU可能只有几十KB内存
- 发布/订阅模式
    - 解耦生产者与消费者：设备无需知道对方地址，通过主题（Topic）通信
    - 支持通配符：+（单层）和#（多层），如home/+/light匹配所有房间灯光
- 服务质量（QoS）分级
    - QoS 0：最多一次（适合实时数据，如股票价格）
    - QoS 1：至少一次（适合指令下发，如开关灯）
    - QoS 2：恰好一次（适合支付等高敏感场景）
- 低功耗与网络适应性
    - 心跳机制（Keep-Alive）维持长连接，比HTTP短连接更省电
    - 支持遗嘱消息（LWT）：设备异常离线时自动通知其他设备

MQTT是一个基于客户端-服务器的消息发布/订阅传输协议。MQTT协议是轻量、简单、开放和易于实现的，这些特点使它适用范围非常广泛。在很多情况下，包括受限的环境中，如：机器与机器（M2M）通信和物联网（IoT）。其在，通过卫星链路通信传感器、偶尔拨号的医疗设备、智能家居、及一些小型化设备中已广泛使用。

有关MQTT的更加详细的说明，以及API说明，可以点击 [MQTT中文手册](https://mcxiaoke.gitbooks.io/mqtt-cn/content/) 查阅。

## Paho部署与应用

### **1. Paho开源MQTT项目介绍**

Paho 是一个为实现 MQTT（Message Queuing Telemetry Transport）和 MQTT-SN（MQTT for Sensor Networks）协议而开发的开源项目，由 Eclipse 基金会托管。MQTT 是一种轻量级的消息传输协议，适用于低带宽、高延迟或不稳定的网络环境，广泛应用于物联网（IoT）、工业监控、智能家居等领域。Paho 项目旨在为不同编程语言提供易于使用的 MQTT 客户端库，帮助开发者快速实现基于 MQTT 协议的消息通信。

![img](./img/rBJlJmepehaAXnBEAACpVtfpYpo547.png)

#### **1.1 Paho特点**

- 多语言支持
    - Paho 提供了多种编程语言的客户端库，包括 Python、Java、C、C++、JavaScript、Go 等。这使得不同技术栈的开发者都能方便地使用 MQTT 协议进行开发，无论是在资源受限的嵌入式设备上使用 C 语言开发，还是在 Web 应用中使用 JavaScript 实现 MQTT 通信。
- 轻量级设计
    - Paho 客户端库的设计注重轻量级和高效性，占用资源少，适合在资源受限的设备上运行，如传感器、微控制器等。这使得它成为物联网设备通信的理想选择。
- 可靠性和稳定性
    - Paho 实现了 MQTT 协议的所有特性，包括不同的服务质量等级（QoS 0、QoS 1、QoS 2），确保消息的可靠传输。同时，它还支持自动重连和持久会话等功能，保证在网络不稳定的情况下，消息通信的稳定性。
- 易于使用
    - Paho 提供了简单易用的 API，开发者可以通过几行代码就实现 MQTT 客户端的连接、发布和订阅功能。这降低了开发者的学习成本，提高了开发效率。

#### **1.2 Paho应用场景**

- 物联网（IoT）
    - 在物联网应用中，大量的设备需要进行数据传输和通信。Paho 的轻量级和多语言支持特性使得它非常适合用于物联网设备的开发，如智能传感器、智能家居设备、工业监控设备等。通过 MQTT 协议，这些设备可以与服务器或其他设备进行实时数据交互。
- 工业自动化
    - 在工业自动化领域，需要实时监控和控制各种生产设备。Paho 可以帮助实现设备之间的消息通信，实现数据的实时采集和控制指令的下发，提高生产效率和质量。
- 移动应用
    - 移动应用通常需要与服务器进行实时数据交互，如即时通讯、实时位置跟踪等。Paho 的 JavaScript 和 Java 客户端库可以方便地集成到移动应用中，实现基于 MQTT 协议的消息通信。

### **3 paho客户端核心结构体**

#### **3.1 连接选项：MQTTClient_connectOptions{}**

该结构体定义了多个设置，用于控制客户端连接到 MQTT 服务器的方式。在连接到 MQTT 代理服务器之前，都必须要定义且设置本结构体。

```
typedef struct
{
	char struct_id[4];     // 结构体标识符，必须是MQTC
	int struct_version;    // 结构体版本，必须是0~8
	int keepAliveInterval; // 保活间隔，单位是秒，默认60秒
	                       // 定义了客户端与服务器之间没有通信的最长时间
	int cleansession;     
	int reliable;          // 控制处于“飞行”状态的消息数量

	MQTTClient_willOptions* will; // 遗嘱相关结构体

	const char* username;  // 用户名，一般为MQTT认证secureId
	const char* password;  // 密码，一般为MQTT认证secureKey

	int connectTimeout;    // 允许连接完成的时间间隔，单位是秒
	int retryInterval;
	MQTTClient_SSLOptions* ssl;
	int serverURIcount;
	char* const* serverURIs;
	int MQTTVersion;

	struct
	{
		const char* serverURI;
		int MQTTVersion;    
		int sessionPresent; 
	} returned;

	struct
	{
		int len;           
		const void* data;  
	} binarypwd;

	int maxInflightMessages;
	int cleanstart;
	const MQTTClient_nameValue* httpHeaders;
	const char* httpProxy;
	const char* httpsProxy;
} MQTTClient_connectOptions;
```



```
// 使用示例（使用系统默认初始化结构体）：
MQTTClient_connectOptions conn_opts = MQTTClient_connectOptions_initializer;
```



#### **3.2 客户端消息：MQTTClient_message{}**

该结构体是MQTT消息负载和属性结构体。注意，消息的主题 `topic` 并不在本结构体中。

```
typedef struct
{
	char struct_id[4];  // 本结构体标识符，必须为MQTM
	int struct_version; // 本结构体版本号，必须为0或1，0代表无消息属性

	int payloadlen;     // 消息负载长度（字节）
	void* payload;      // 消息负载

	int qos;            // QoS等级：
    					// 0: 最多传1次
    					// 1: 最少传1次
    					// 2: 精确传1次

	int retained;       // 保留标识：
						// 对于发布者发布时，true表示服务器应保留该消息，false则不保留
						// 对于订阅者接收时，true表示该消息是服务器保留的，false则是新消息

	int dup;
	int msgid;
	MQTTProperties properties;
} MQTTClient_message;
```



```
// 使用示例（使用系统默认初始化结构体）：
MQTTClient_message pubmsg = MQTTClient_message_initializer;
```



### **4 paho客户端核心API**

如上节所述，Paho为了方便用户使用，提供了同步和异步两种API，它们在功能上是相同的，下面以同步libpaho-mqtt3c 同步接口为例，介绍相关的核心结构体和API。

#### **4.1 创建MQTT客户端**

此函数创建一个 MQTT 客户端，准备连接到指定的服务器，并使用指定的持久化存储策略。

```
int MQTTClient_create(MQTTClient *handle,
					  const char *serverURI,
					  const char *clientId,
					  int persistence_type,
					  void *persistence_context)	
```



- 参数

    - **handle** - 客户端句柄，在该函数成功返回后，句柄将被填充为有效的客户端引用

    - **serverURI** - 服务器地址，格式是 `协议://主机:端口`

    - **clientId** - 设备ID

    - persistence_type

         

        \- 存储策略，有如下取值：

        - MQTTCLIENT_PERSISTENCE_NONE：使用内存中的持久化。如果客户端正在运行的设备或系统出现故障或关闭，任何正在传输的消息的当前状态将丢失，并且即使在 QoS1 和 QoS2 的情况下，某些消息也可能无法传递。
        - MQTTCLIENT_PERSISTENCE_DEFAULT：使用默认的（基于文件系统的）持久化机制。正在传输的消息的状态保存在持久存储中，在出现意外故障的情况下提供一定的消息丢失防护。
        - MQTTCLIENT_PERSISTENCE_USER：使用特定于应用程序的持久化实现。使用这种类型的持久化将持久化机制的控制权交给应用程序。应用程序必须实现MQTTClient_persistence接口。

    - persistence_context

         

        \- 配合存储策略的持久化上下文，有如下取值：

        - 如果应用程序使用无 MQTTCLIENT_PERSISTENCE_NONE 持久化，则此参数未被使用，应设置为 NULL。
        - 对于默认 MQTTCLIENT_PERSISTENCE_DEFAULT 持久化，应将其设置为持久化目录的位置（如果设置为 NULL，则使用的持久化目录为工作目录）。
        - 使用用户自定义 MQTTCLIENT_PERSISTENCE_USER 持久化的应用程序将此参数设置为指向有效的MQTTClient_persistence结构。

- 返回值

    - 成功返回MQTTCLIENT_SUCCESS
    - 失败返回错误码

#### **4.2 设置回调**

此函数为指定客户端设置回调函数。如果客户端应用程序不使用特定的回调，则将相关参数设置为 NULL（ma除外）。调用该函数会将客户端置于多线程模式。任何必要的消息确认和状态通信都在后台处理，无需客户端应用程序的任何干预。

```
int MQTTClient_setCallbacks(MQTTClient handle,
							void *context,
							MQTTClient_connectionLost *cl,
							MQTTClient_messageArrived *ma,
							MQTTClient_deliveryComplete *dc)	
```



- 注意：调用此函数时，MQTT 客户端必须处于断开连接状态，或在连接之前调用。
- 参数
    - **handle** - 从 MQTTClient_create()返回的有效客户端句柄
    - **context** - 上下文指针，它将被传递给每个回调函数，以便在回调中提供对上下文的访问，可以为NULL
    - **cl** - connection lost，连接丢失的回调函数，可以设置为NULL
    - **ma** - message arrived，消息到达的回调函数
    - **dc** - delivery complete，消息交付完成的回调函数，可以设置为NULL
- 返回值
    - 成功返回MQTTCLIENT_SUCCESS
    - 失败返回错误码

#### **4.3 连接MQTT服务器**

此函数使用指定的选项将先前创建的客户端连接到 MQTT 服务器。

```
int MQTTClient_connect(MQTTClient handle,
					   MQTTClient_connectOptions *options)
```



- 参数
    - **handle** - 从 MQTTClient_create()返回的有效客户端句柄
    - **options** - MQTTClient_connectOptions{}结构体，用于指定连接选项
- 返回值
    - 成功返回MQTTCLIENT_SUCCESS
    - 失败返回大于0的错误码，具体如下：
        - 1：连接被拒绝：不可接受的协议版本
        - 2：连接被拒绝：标识符被拒绝
        - 3：连接被拒绝：服务器不可用
        - 4：连接被拒绝：用户名或密码错误
        - 5：连接被拒绝：未授权
        - 6~255：为未来使用保留

#### **4.4 订阅主题**

此函数尝试帮客户端订阅指定主题，该主题可能包含通配符。此调用还指定了订阅所需的服务质量QoS。

```
int MQTTClient_subscribe(MQTTClient handle,
						 const char *topic,
						 int qos)	
```



- 参数
    - **handle** - 有效客户端句柄
    - **topic** - 订阅的主题，可包含通配符
    - **qos** - 服务质量
- 返回值
    - 成功返回MQTTCLIENT_SUCCESS
    - 失败返回错误码

#### **4.5 发布消息**

此函数尝试将消息发布到给定主题，成功发布后，会触发得到一个 形如 `MQTTClient_deliveryToken` 的所谓交付令牌，该参数实质就是一个 `int` 整型数据，用来告知客户端消息是否被成功交付。

```
int MQTTClient_publishMessage(MQTTClient handle,
							  const char *topicName,
							  MQTTClient_message *msg,
							  MQTTClient_deliveryToken *dt)	
```



- 参数
    - **handle** - 客户端句柄
    - **topicName** - 主题名
    - **msg** - 消息内容
    - **dt** - 消息交付令牌，可设为NULL
- 返回值
    - 成功返回MQTTCLIENT_SUCCESS
    - 失败返回错误码
