# 写作与笔记规范

> 本文件是命名、目录、frontmatter、新建流程、检索和文风的唯一来源；`AGENTS.md` 只保留摘要与入口。

## 1. 命名规范

- 目录与文件以中文为主，技术专名保留英文（LVGL、STM32、gcc）。
- 禁止英文小写碎片命名（`url.md`、`code.md`）。产品名、协议名、命令名、芯片型号属专名，允许保留（`bash.md`、`vim.md`、`docker.md`、`cc2530.md`）；通用名词或动词碎片不允许。
- 不用期号或日期做目录层级；主题名不加数字序号前缀。资料与附件目录（如开题报告、任务书）不受序号限制。
- 图片统一放笔记所在目录的 `img/` 子目录。
- MOC 作用域：`项目/`、`本机/`、`规范/` 各有顶层 `MOC.md`；`X-工具与方法/` 及其子目录按需建 MOC，统一索引其全部子目录；子目录默认复用上级 MOC，需要独立入口时另建子 MOC。基础设施目录（`script/`、`.skills/`、`.cursor/`、`self/`、`img/`）和资料/附件目录不要求 MOC。

## 2. frontmatter

每篇笔记头部必须带统一属性；`README模板` 等非笔记文件除外。必填字段为 `type`、`tags`、`status`、`created`、`updated`；推荐字段为 `target`、`input`、`output`、`review`、`related`。字段含义、取值范围和模板清单见 [[模板说明]]。

```yaml
---
type: 概念
layer: L1
domain: mcu
tags: [stm32, linux]
status: 进行中
created: 2026-01-01
updated: 2026-01-01
target: 晶体
prereq: ["[[GPIO]]"]
input: 课程第 3 讲
output: 时序图与测试代码
review: 2026-10-20
related: ["[[串口通信]]"]
---
```

`课程` 只作为 `input` 的来源描述，不再作为 `type`、标签或目录边界；层级与领域取值见 [[知识分层方案]]。

校验命令与提交前检查见 [校验与提交规范](./校验与提交规范.md)。

## 3. 新建笔记流程

1. 从 `模板/` 复制对应模板；先读 [[模板说明]] 选择类型。
2. 确定 `layer` 与 `domain`，再填写必填字段与 `prereq`；按需补推荐字段。
3. 填写正文；摘录必须用自己的话重写，行文遵循本文件第 5–7 节。
4. 接入已有知识：涉及仓库内已有知识点时用双链 `[[笔记名]]` 连接，并在 `related` 登记；已有笔记定义不完整时先补全该笔记，再建立双链。
5. 把新笔记加入所属 `MOC.md` 索引；子目录默认加入上级 MOC。

重命名或删除笔记时，同步更新引用它的 `MOC.md` 与正文双链；提交前用 `grep -rn "旧笔记名" --include="*.md" .` 检查残留。

## 4. 检索方式

```bash
grep -rn "^type: 踩坑" --include="*.md" .     # 按类型
grep -rln "^tags:.*stm32" --include="*.md" .   # 按标签
grep -rn "^layer: L1" --include="*.md" .       # 按能力层级
grep -rn "^domain: mcu" --include="*.md" .     # 按技术领域
grep -rn "^review: 2026-10" --include="*.md" . # 按复习月份
```

Obsidian 可用属性面板或 Bases 视图；`MOC.md` 静态索引是权威入口。

## 5. 写作顺序

| 类型 | 顺序 |
| --- | --- |
| 原理、工具、协议 | 定义与边界 → 符号与假设 → 机制推导 → 操作步骤 → 验证 → 结论与适用边界 |
| 踩坑 | 现象 → 可达性或状态条件 → 证据 → 根因 → 修复 → 回滚与验证 |

每节只承担一个论证任务；标题使用名词性主题或明确判断，不使用口语化标题。命令放在最小模型之后。

## 6. 概念、图与证据

### 6.1 概念与术语

- 首次出现的概念必须给出定义；再按适用维度补充持有方、作用域、输入、输出、机密性或验证者，通常选 2–3 项。
- 相近概念必须显式区分，例如主机密钥与用户密钥、私钥与私钥口令、文件容器格式与密钥算法。
- 术语选定后全文一致；英文专名首次可标注原文，后续不混用别名、口语名和模糊简称。
- 容器名不等于内容名；例如 `.pem` 是容器，文件可能承载私钥、证书或其他对象。

### 6.2 形式化表达与图

- 文字定义概念，公式表达约束和不变量，表格整理离散事实，图表达空间结构、时序关系、状态迁移或决策路径。
- 涉及条件、状态、协议、认证、依赖关系时，优先用公式、集合、谓词、状态转移或表格表达。
- 公式中的符号必须先定义；充要条件用 `⇔`，合取/析取用 `∧`/`∨`，成员关系用 `∈`。
- 达到规模时配图：两方以上交互用时序图；三个以上模块、目录、硬件单元或跨信任边界用组件图或部署图；三个以上状态用状态机图；两个以上分支用流程图或决策树；三篇以上笔记的依赖用关系图。低于规模时用编号列表或表格。
- 图默认使用 Mermaid 源码，代码块语言标注为 `mermaid`；用户明确要求 PlantUML，或确认 Obsidian 已安装并启用 PlantUML 插件时才使用 PlantUML。
- 图前写编号与图题（如 `图 1 ...`）；短笔记只有一张图时可省略编号，保留图题。图中术语、符号、编号与正文一致；箭头方向、触发条件、数据流与控制流必须明确；跨信任域时画出信任边界。
- 图后用一段文字陈述关键结论或不变量；图用于建立结构直觉，不替代定义和推导。
- 可维护的知识用源码图；截图仅用于记录真实 GUI、硬件现象或错误现场。
- 简单线性步骤用编号列表；图必须降低理解成本，不能作为装饰。

### 6.3 证据与操作

- 区分事实、观察、推断和建议；命令、日志、文档来源属于证据，推断必须能由证据推出。
- 操作命令写清前置条件、适用系统、验证方法和回滚路径；占位符必须显式标注，不写入真实密钥、token 或敏感主机信息。
- 保留可复现实验步骤、权限要求、错误现象和排查表。
- 外部事实、兼容性结论和版本依赖保留来源链接，注明适用范围与访问日期；链接失效时补充替代来源。

## 7. 语言约束

- 直接陈述定义、条件、推导和结论；不使用铺垫、夸张、反问、推销腔或焦虑腔。
- 禁用对偶式生硬转折，如“不是 X，而是 Y”；需要区分时直接分别定义。
- 禁用口语和含糊措辞，如“搞、挂、一把、主力、本质上、其实”；“基本上、最好、较差”须给出量化依据，否则改写为具体条件。
- 不将软件拟人化；软件没有“认为/觉得”，只存在输入、解析、状态和返回结果。
- 同一结论只出现一次；图题、图后结论和必要的定义复述除外。重复内容合并为定义、条件或表格。

## 8. 完成检查

1. frontmatter 必填字段齐全，`updated` 已更新。
2. 新笔记已加入所属 MOC；重命名后无残留引用。
3. 双链与 `related` 一致，断链数为 0。
4. 图表编号、图题、箭头语义和图后结论齐全。
5. 无真实 IP、token、凭据或个人信息。
6. `python script/notes_lint.py --strict` 通过。
