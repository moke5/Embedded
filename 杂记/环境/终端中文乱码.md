# 终端中文乱码

[toc]

> 场景：脚本输出中文、或查看中文日志时，在终端里显示乱码。这个问题同时涉及 Linux（WSL2 Ubuntu + bash）和 Windows（PowerShell），**两侧的排查命令、默认编码、修复方法都不一样**，下面分开写。

## 一、原理：乱码的本质

乱码不是字节坏了，而是**同一串字节被两种不同的编码各自解释了一遍**。

字符在计算机里存的是一串字节（bytes）。把字符变成字节叫「编码」，把字节变回字符叫「解码」。这两步必须用同一套规则（UTF-8、GBK 等），对不上就会乱码：

```mermaid
flowchart LR
    SRC["字符（中文）"] -->|"编码① 用某规则变字节"| BYTE["字节流<br/>E8 84 9A ..."]
    BYTE -->|"解码② 用某规则变字符"| VIEW["屏幕显示"]
    VIEW -- "① ≠ ②" --> BAD["乱码"]
```

这条链路，既适用于「脚本往终端打印」，也适用于「读取文件内容」。凡是乱码，都是链路上「产生字节的一端」和「解释字节的一端」编码不一致。

### 两个容易混淆的概念

- **乱码**：编码、解码规则不同，但字节恰好都是"合法字节"，不报错、只显示错。
- **报错**：Python 的 stdout 被限制成 ASCII、内容是中文时，直接抛 `UnicodeEncodeError`，这是编码声明不够，不是乱码。

### 三种典型乱码形态，用来判断方向

| 看到的样子 | 实际发生了什么 |
| --- | --- |
| `脚本` → `鑴氭湰` | UTF-8 字节被 **GBK** 解码 |
| `中文` → `涓枃` | UTF-8 字节被 **GBK** 解码 |
| `中文` → `ä¸æ–‡`、`` | GBK 字节被 **UTF-8** 解码 |

先认准是「UTF-8 内容被 GBK 读」还是「GBK 内容被 UTF-8 读」，再动手改，不容易改成反效果。

## 二、Linux 侧（WSL2 Ubuntu / bash）

### 排查命令

```bash
# 1. 当前 locale（决定程序 stdout 编码的关键）
locale
echo $LANG

# 2. Python 实际往 stdout 写字节时用什么编码
python3 -c "import sys; print(sys.stdout.encoding)"

# 3. 文件本身是什么编码（源码/日志的编码，和运行时输出是两回事）
file -i 你的脚本.sh
```

判读：

- `locale` 输出只要以 `UTF-8` 结尾（`C.UTF-8`、`zh_CN.UTF-8` 都算），就是对的，不用改。只有 `C` / `POSIX` 这种不带 UTF-8 的才需要修。
- 第 2 步不是 `utf-8` → Python 环境问题，走下面的「修复 Python 输出」。
- 第 3 步不是 `utf-8` → 源文件编码问题，用 UTF-8 重新保存文件。

### 修复

```bash
# locale 不是 UTF-8 时才需要（C.UTF-8 已正确就不用做这步）
sudo locale-gen zh_CN.UTF-8
sudo update-locale LANG=zh_CN.UTF-8
export LANG=zh_CN.UTF-8
export LC_ALL=zh_CN.UTF-8

# 强制 Python 输出 UTF-8（写入 ~/.bashrc 可持久化）
export PYTHONIOENCODING=utf-8
```

脚本内兜底（不依赖环境）：

```python
import sys
sys.stdout.reconfigure(encoding='utf-8')
print("中文")
```

## 三、Windows 侧（PowerShell）

Windows 上的编码命令和 Linux 完全不同，这块最容易踩坑。

### 排查命令

```powershell
# 1. 控制台代码页：936=GBK，65001=UTF-8（只影响控制台显示，不影响 Get-Content）
chcp

# 2. PowerShell 往控制台「显示」字符用的编码
[Console]::OutputEncoding

# 3. PowerShell 读文件时「默认」用的编码（重点！）
#    中文 Windows 上返回 gb2312/936，意味着 Get-Content 默认按 GBK 读文件
[System.Text.Encoding]::Default

# 4. 查看文件字节头，判断编码：EF BB BF = UTF-8 BOM，FF FE = UTF-16 LE
Format-Hex -Path .\log\obsidian.log -Count 16
```

判读：

- 第 4 步见 `EF BB BF` 开头 → 文件是 UTF-8（带 BOM）；没有任何 BOM 字节 → 大概率是 UTF-8（无 BOM），但也可能是 GBK，需结合内容判断。
- 文件是 UTF-8，但 `cat` 乱码 → 就是下面这个陷阱。

### 关键陷阱：`chcp` 改不了 `cat` 的默认编码

很多人以为 `chcp 65001` 之后 PowerShell 就"全 UTF-8"了，不是：

- `chcp 65001` 只改**控制台代码页**，管的是「字符显示到屏幕上用哪套编码」。
- 而 PowerShell 5.1 的 `cat`（`Get-Content` 的别名）读文件时，默认用 `[System.Text.Encoding]::Default`，也就是**系统的 ANSI 默认编码（GBK）**，跟 `chcp` 没关系。

所以对一个 UTF-8 文件：

1. `Get-Content` 先用 GBK 把 UTF-8 字节**解码**成错误的字符串 `鑴氭湰`（乱码在这一步就发生了）；
2. 这个错误字符串再被输出到屏幕，此时控制台已 `chcp 65001`（UTF-8），于是你把 `鑴氭湰` 这几个"错字"**清晰地**显示了出来。

结论：`chcp 65001` 之后乱码依然在，只是乱码字本身显示得很清楚而已。

### 修复

**读 UTF-8 文件，显式指定编码**（最直接）：

```powershell
Get-Content -Encoding UTF8 .\log\obsidian.log
# 或 cat 别名
cat -Encoding UTF8 .\log\obsidian.log
```

**让控制台输出/交互也走 UTF-8**（处理脚本通过 PowerShell 打印、或和 WSL/Python 交互时的乱码）：

```powershell
chcp 65001
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8   # 往本机命令(wsl/python)传文本用的编码
$InputEncoding  = [System.Text.Encoding]::UTF8   # 读本机命令输出用的编码
```

**根本办法：换 PowerShell 7（pwsh）**。PowerShell 7 的 `Get-Content` 默认就是 UTF-8（无 BOM 也按 UTF-8 读），`cat` 读 UTF-8 日志不会再乱码。Windows 自带的是 5.1（`powershell.exe`），5.1 才默认 GBK。

## 四、实战案例：日志乱码排查

以 `start_obsidian.sh`（WSL2 里跑的 bash，中文用 UTF-8 写日志到 `log/obsidian.log`）为例，完整走一遍：

```bash
# Linux 侧确认：locale 已经是 UTF-8，脚本输出没问题
<用户>@<主机>:/mnt/d/git/embedded$ locale
LANG=C.UTF-8          # ← 已是 UTF-8，这一侧没问题

# 但到 Windows 侧用 PowerShell 查看同一份日志
PS D:\git\embedded> chcp 65001        # 已经是 65001，控制台是 UTF-8 了
Active code page: 65001

PS D:\git\embedded> cat .\log\obsidian.log
[+2026-10-13 18:10:15] 鑴氭湰鑷韩杩涚▼ PID:783      # ← 还是乱码
```

为什么 `chcp` 已经 65001 还乱？对照上面第三节：

- 日志文件是 UTF-8（`脚本自身进程 PID:783`）；
- `cat`（`Get-Content`）默认按 GBK 读取 → `脚本` 变成 `鑴氭湰`；
- `chcp 65001` 只影响屏幕显示，不影响 `Get-Content` 的解码。

正确读法：

```powershell
cat -Encoding UTF8 .\log\obsidian.log
# [+2026-10-13 18:10:15] 脚本自身进程 PID:783
```

所以这里**不需要改 Linux 的 locale，也没坏什么**，只是 PowerShell 5.1 读文件默认用 GBK。要么显式 `-Encoding UTF8`，要么换 pwsh。

## 五、小结

1. 乱码的根因永远只有一个：**产生字节的一端和解释字节的一端，用了两套编码**。
2. 排查先分清是哪一端：Linux 用 `locale` / `file -i`，Windows 用 `chcp` / `[Console]::OutputEncoding` / `[System.Text.Encoding]::Default` / `Format-Hex`。
3. Linux 侧只要 locale 以 `UTF-8` 结尾就是对的，别盲目改。
4. Windows 侧最大的坑：**`chcp 65001` 只管控制台显示，管不了 `Get-Content`/`cat` 读文件的默认 GBK 解码**；读 UTF-8 文件要 `Get-Content -Encoding UTF8`，或直接换 pwsh。

编码系统的概念（字符集 vs 编码方案、Unicode 与 UTF 的区别）见 [杂谈](../Linux/杂谈.md) 的「编码系统」一节。
